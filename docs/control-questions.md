# Контрольные вопросы и ответы

**НИиСПО · Лабораторная работа № 1 · Han Yu · группа 13**

Вопросы приведены в порядке методических указаний БГУ (2026, с. 35–37). Номера 1–9 относятся к с. 35, 10–22 — к с. 36, 23–32 — к с. 37. Команды в ответах иллюстрируют понятия. Результаты выполненных заданий приведены в отдельном [отчёте](report.md).

### 1. Что такое Docker и зачем он нужен? В чём ключевые преимущества для разработки и эксплуатации? Какие есть альтернативные системы контейнеризации и в каких сценариях они предпочтительнее (например, Podman, containerd)?

Docker позволяет собрать приложение вместе с его зависимостями в образ и запустить его изолированно. Один артефакт можно проверять в CI и передавать на сервер, сохраняя версии библиотек. Linux-контейнеры разделяют ядро хоста или Linux-ВМ Docker Desktop. Podman удобен для запуска от обычного пользователя без постоянного центрального демона. containerd управляет жизненным циклом контейнеров и подходит, например, в качестве среды исполнения на узле Kubernetes. [Podman](https://podman.io/) · [containerd](https://containerd.io/)

### 2. Что такое Docker‑образ? Как его получить (из реестра, через сборку, из контейнера)? В чём разница между образом и контейнером?

Образ содержит слои файловой системы и конфигурацию запуска. Контейнер — экземпляр образа со своим записываемым слоем и состоянием процессов. Образ можно загрузить (`docker pull nginx:alpine`), собрать из Dockerfile (`docker build -t site:v1 .`) или получить из изменений контейнера (`docker commit mynginxlast site:snapshot`). Содержимое подключённых томов в `commit` не входит. Dockerfile сохраняет рецепт сборки для следующего разработчика.

### 3. Как запустить контейнер? Как пробросить порты, чтобы получить доступ к сервису снаружи? Как задать имя контейнера и ограничить ресурсы (CPU/RAM)?

Команда `docker run -d --name site -p 127.0.0.1:8080:80 --cpus=1 --memory=128m nginx:alpine` создаёт и запускает контейнер. Сервис слушает порт 80 внутри, а браузер хоста обращается к `localhost:8080`. Для доступа с других машин задают нужный сетевой интерфейс хоста и разрешают входящий трафик. `--cpus` ограничивает процессорное время, `--memory` задаёт лимит памяти.

### 4. Как просмотреть логи контейнера? Как фильтровать логи по времени, по строкам, по уровню (например, ошибки)? Как настроить ротацию логов?

`docker logs --since 15m --tail 100 -f site` выводит последние строки за заданный период и продолжает следить за новыми. Границу конца интервала задаёт `--until`. Приложение должно писать в stdout/stderr. В PowerShell строки ошибок можно отобрать командой `docker logs site 2>&1 | Select-String 'ERROR|FATAL'`. Уровень задаётся форматом журнала приложения. Для ротации при создании контейнера можно задать `--log-driver json-file --log-opt max-size=10m --log-opt max-file=3` или выбрать драйвер `local`. [Драйверы журналирования](https://docs.docker.com/engine/logging/configure/)

### 5. Как сохранить данные внутри контейнера между перезапусками? В чём разница между volume, bind mount и tmpfs? Как правильно выбрать тип хранения для базы данных, кеша, логов?

Перезапуск того же контейнера сохраняет его записываемый слой. Для данных, которые должны пережить **замену** контейнера, используют внешнее хранилище. Именованным томом управляет Docker, поэтому в задании 4 каталог PostgreSQL подключён к `dbdata`. Bind mount привязывает конкретный путь хоста, что удобно для HTML и конфигурации Nginx. `tmpfs` хранит временные данные в памяти до остановки контейнера и подходит для восстанавливаемого кеша. Обычные журналы лучше выводить в stdout/stderr и настраивать ротацию. [Хранение данных](https://docs.docker.com/engine/storage/)

### 6. Как подключить контейнеры к одной сети? Какие типы сетей бывают (bridge, host, overlay) и для чего используется каждая? Какие есть альтернативы (например, без сетей Docker)?

`docker network create lab-net` создаёт пользовательскую bridge-сеть. К ней подключают новый контейнер через `--network lab-net`, существующий — командой `docker network connect lab-net site`. Bridge соединяет контейнеры одного хоста. Host использует сетевое пространство хоста. Overlay объединяет узлы через виртуальную сеть, например в Swarm. Режим `none` оставляет контейнер без внешней сети. Можно также обращаться к сервису по опубликованному порту хоста. [Сетевые драйверы](https://docs.docker.com/engine/network/)

### 7. Почему контейнеры могут обращаться друг к другу по имени? Как Docker разрешает имена внутри сети (DNS, service discovery)? Что происходит, если имя сервиса меняется или контейнер перезапускается?

В пользовательской сети встроенный DNS Docker разрешает имена контейнеров и сетевые псевдонимы. В Compose имя сервиса служит таким псевдонимом, поэтому API подключается к `db:5432`. При пересоздании контейнера IP может измениться. Клиенту нужно установить новое соединение и заново разрешить имя. При переименовании сервиса обновляют настройки клиентов либо сохраняют прежнее имя как сетевой псевдоним. [Сети и DNS](https://docs.docker.com/engine/network/)

### 8. Что такое метки (docker tag)? Как правильно добавлять метки образам (семантика, latest vs конкретные теги, best practices)? Как удалить теги и чем это отличается от удаления образов?

Тег — именованная ссылка на образ. `docker tag lab1-task2:v1 hy20010919/lab1-task2:v1` добавляет имя для публикации в нужном репозитории. Для релиза полезен тег версии или идентификатор коммита. `latest` — обычный изменяемый тег, он не определяет самую новую версию. Для строгой воспроизводимости используют digest `sha256`. `docker image rm repo:v1` снимает ссылку, а другие теги того же образа могут сохраниться. Общие слои освобождаются лишь после исчезновения ссылок на них.

### 9. Как удалить ненужные образы и контейнеры? Как автоматизировать очистку (команды, скрипты, политики)? Как избежать случайного удаления работающих контейнеров?

Сначала смотрят `docker ps -a` и `docker image ls`. Завершённый учебный контейнер удаляют по имени через `docker rm`, ненужный тег — через `docker image rm`. Для автоматизации можно помечать временные контейнеры при запуске (`--label purpose=lab-temp`) и периодически выполнять `docker container prune --filter label=purpose=lab-temp`. Эта команда выбирает остановленные контейнеры. `docker image prune` по умолчанию очищает висячие образы. Для рабочего стенда следует проверить область фильтра и избегать принудительного удаления.

### 10. Как выполнить команду внутри работающего контейнера? В чём разница между docker exec и docker attach? Когда лучше использовать entrypoint/cmd вместо exec?

`docker exec -it mynginxlast sh` открывает новый процесс внутри работающего контейнера. Выход из него оставляет Nginx работающим. `docker attach` подключает терминал к существующим потокам главного процесса. Ввод и сигналы могут воздействовать на сам сервис. Постоянную команду запуска задают через `ENTRYPOINT` и `CMD`, чтобы сервис запускался при каждом создании контейнера. `exec` удобен для разовой диагностики.

### 11. Как узнать, какие файлы изменяет программа внутри контейнера? Как сравнить слои образа? Как получить diff изменений в файловой системе контейнера?

`docker diff site` показывает изменения записываемого слоя контейнера относительно образа. Буквы `A`, `C` и `D` обозначают добавление, изменение и удаление. Изменения внутри подключённого тома исследуют отдельно. `docker history --no-trunc IMAGE` показывает команды и размеры слоёв. Для сравнения двух образов можно сопоставить их списки `RootFS.Layers` через `docker image inspect`. Для просмотра файлов по слоям подойдёт `dive`.

### 12. Когда происходит завершение контейнера? Как корректно остановить контейнер (graceful shutdown)? Как настроить сигналы остановки (stop_grace_period) и обработку SIGTERM?

Контейнер останавливается, когда завершается главный процесс (PID 1 в обычном контейнере). `docker stop` обычно посылает SIGTERM, ждёт отведённое время и при необходимости отправляет SIGKILL. Приложение должно принять сигнал, завершить текущие запросы и закрыть соединения с БД. Exec-форма `CMD` передаёт сигнал непосредственно серверу. В Compose `stop_signal: SIGTERM` задаёт сигнал, `stop_grace_period: 30s` даёт время для завершения.

### 13. Как работает кеширование слоев при сборке образа? Почему важен порядок инструкций в Dockerfile для ускорения пересборки? Объясните причины ускорения/замедления: кеш слоёв, порядок инструкций, multi‑stage, .dockerignore. Как измерить время сборки и как понять, какой слой пересобирался?

BuildKit повторно использует результат шага, когда совпадают инструкция и значимые входные данные. Изменение файла делает зависящий от него шаг и последующие зависимые шаги кандидатами на пересборку. В этой работе `requirements.txt` обрабатывается до копирования `app.py`, поэтому правка маршрута позволяет повторно использовать слой библиотек. `.dockerignore` сокращает контекст, а отдельный этап сборки может использовать свой кеш. Для сравнения в PowerShell используют `Measure-Command { docker build --progress=plain -t trial . }` и отдельно смотрят отметки `CACHED` в журнале повторной сборки. Условия холодного и тёплого запуска фиксируют отдельно. [Кеш сборки](https://docs.docker.com/build/cache/optimize/)

### 14. К какому количеству слоёв стремиться в образе? Какие правила оптимизации слоёв (объединение RUN, порядок инструкций, очистка кеша менеджера пакетов)? Как оценить размер образа и его состав (слои, файлы)?

Универсального числа слоёв нет. Для скорости важны границы кеширования, а для объёма — какие данные попадут в итоговые слои. Установку системных пакетов и очистку списков пакетов выполняют в одном `RUN`, потому что удаление файла в следующем слое оставляет его в предыдущем. Часто меняющийся код копируют после зависимостей. `docker image ls` показывает размеры образов, `docker history IMAGE` — вклад команд, а `dive IMAGE` помогает найти крупные файлы. Общие слои нескольких тегов не следует суммировать как независимый расход диска.

### 15. Опишите базовые команды Dockerfile: FROM, RUN, COPY, ADD, WORKDIR, ENV, EXPOSE, CMD, ENTRYPOINT. Что они делают, какие есть частые ошибки и антипаттерны? Где смотреть официальную документацию и как проверять Dockerfile на ошибки (hadolint)?

`FROM` выбирает базу этапа. `RUN` выполняет команду во время сборки. `COPY` переносит файлы, `ADD` дополнительно обрабатывает некоторые архивы и удалённые источники. `WORKDIR` задаёт рабочий каталог, `ENV` сохраняет значения для следующих шагов и запуска. `EXPOSE` документирует порт. `CMD` задаёт команду или аргументы по умолчанию, `ENTRYPOINT` — исполняемый процесс. Частые ошибки — копирование всего проекта до установки зависимостей, секреты в слоях и ожидание, что `EXPOSE` сам опубликует порт. Статическую проверку запускают командой `hadolint Dockerfile`. [Справочник Dockerfile](https://docs.docker.com/reference/dockerfile/) · [Hadolint](https://github.com/hadolint/hadolint)

### 16. Что такое контекст сборки? Как он передаётся в Docker и как влияет на COPY/ADD? Как оптимизировать контекст (размер, .dockerignore), чтобы ускорить сборку и уменьшить размер образа?

Контекст — набор входных файлов, доступных сборщику. В `docker build -f task2/Dockerfile task1` контекстом служит каталог `task1`, поэтому `COPY index.html ...` читает файл именно оттуда. Путь к Dockerfile и корень контекста могут различаться. Builder получает необходимые входные данные из указанного каталога или удалённого источника. Узкий контекст и `.dockerignore` исключают каталоги `.git`, виртуальную среду и локальные секреты. Это сокращает передачу данных и предотвращает их случайное включение через `COPY . .`.

### 17. В чем разница между COPY и ADD? Когда нужно использовать ADD?

`COPY` подходит для локальных файлов и каталогов. Флаг `--from` позволяет взять артефакт другого этапа. `ADD` также умеет получить поддерживаемый удалённый источник или автоматически распаковать локальный tar-архив. Например, `ADD site.tar.gz /srv/site/` подходит, если требуется именно распаковка. Для обычного HTML достаточно `COPY`. [Справочник Dockerfile](https://docs.docker.com/reference/dockerfile/)

### 18. В чем разница между CMD и ENTRYPOINT? Как они взаимодействуют друг с другом?

В exec-форме `ENTRYPOINT ["uvicorn"]` задаёт программу, а `CMD ["app:app", "--host", "0.0.0.0"]` — её аргументы по умолчанию. Аргументы после имени образа в `docker run` заменяют `CMD` и передаются существующему `ENTRYPOINT`. Если `ENTRYPOINT` отсутствует, `CMD` может задавать всю команду. Поэтому в наших v5 и v6 команда `docker run --rm simple_python_app:v6 id` запускает `id` вместо Uvicorn. Сам `ENTRYPOINT` можно переопределить через `--entrypoint`.

### 19. В чем разница между ARG и ENV? Доступны ли ARG во время выполнения контейнера?

`ARG` задаёт параметр сборки, который передают через `--build-arg` и используют в области видимости его объявления. При запуске приложения этот параметр автоматически в окружении не появляется. `ENV` сохраняется в конфигурации образа, доступен при запуске и может быть переопределён через `docker run -e`. Если скопировать значение `ARG` в `ENV` или в файл, оно сохранится. Для токенов при сборке используют секреты BuildKit.

### 20. Что такое Multi-stage builds (многоэтапная сборка)? Приведите пример, когда это необходимо (например, сборка Go/React приложения и копирование только бинарника в финальный образ).

Несколько инструкций `FROM` образуют отдельные этапы. Go-программу можно скомпилировать в этапе с SDK, а в финальный образ скопировать только подходящий исполняемый файл и необходимые данные. В нашем v5 первый этап создаёт wheels, второй устанавливает пакеты из `/wheels` без обращения к индексу. Каталог wheels остаётся в конечном образе этой реализации, что помогает объяснить его размер. Окончательный эффект проверяют измерением.

### 21. Из каких компонентов состоит Docker Engine?

CLI `docker` передаёт запросы по API демону `dockerd`. Демон управляет образами, контейнерами, сетями и томами. На Linux он использует `containerd` для жизненного цикла контейнеров, а OCI-runtime, обычно `runc`, создаёт изолированный процесс с заданными пространствами имён и ограничениями ресурсов. В Docker Desktop для Windows Linux-демон работает в Linux-среде.

### 22. Как посмотреть подробную информацию о контейнере (IP-адрес, смонтированные volumes, переменные окружения)? Привести примеры команды.

`docker inspect mynginxsite` выдаёт полное JSON-описание. Для адресов по сетям удобно выполнить `docker inspect --format '{{json .NetworkSettings.Networks}}' mynginxsite`, для томов и bind mount — `docker inspect --format '{{json .Mounts}}' mynginxsite`. Переменные показывает `docker inspect --format '{{json .Config.Env}}' mynginxsite`. Для сервиса БД такой вывод может содержать пароль, поэтому его не публикуют в отчёте.

### 23. Как посмотреть потребление ресурсов (CPU, RAM) контейнером в реальном времени?

`docker stats` обновляет CPU, память с лимитом, сеть и дисковые операции для работающих контейнеров. `docker stats postgres-db` показывает один контейнер, `docker stats --no-stream postgres-db` снимает разовое показание. Для сравнения двух сборок нужны одна и та же нагрузка и одинаковый интервал наблюдения.

### 24. Основные возможности Docker Compose: сервисы, тома, сети, секреты, профили, зависимости. В чём отличие между docker-compose (отдельный бинарный файл) и docker compose (модуль)? Какие возможности есть только в новом модуле?

Compose описывает в YAML сервисы, образы и сборку, сети, тома, секреты и зависимости. Профили включают дополнительные сервисы только в выбранном сценарии. Исторический `docker-compose` v1 был написан на Python. Современная реализация на Go интегрирована в Docker CLI и вызывается как `docker compose`. Например, появившийся с v2.22 режим `develop.watch` синхронизирует файлы или пересобирает сервис при изменениях. Версию установленного модуля показывает `docker compose version`. [История Compose](https://docs.docker.com/compose/intro/history/) · [Compose Watch](https://docs.docker.com/compose/how-tos/file-watch/)

### 25. Как в Docker Compose настроить порядок запуска сервисов с учетом их готовности?

Краткая форма `depends_on` задаёт порядок запуска. Если API требуется готовая БД, у БД описывают `healthcheck`, а у API — зависимость `db` с условием `condition: service_healthy`. Тогда Compose дождётся успешной проверки перед запуском API. Для одноразового задания, например миграции, можно использовать `service_completed_successfully`. Позднейшие обрывы соединения приложение обрабатывает при работе. [Порядок запуска](https://docs.docker.com/compose/how-tos/startup-order/)

### 26. Что такое Healthcheck в Docker и Docker Compose? Как он работает и зачем нужен?

Healthcheck периодически выполняет команду внутри контейнера. После начального состояния `starting` успешная проверка даёт `healthy`, а заданное число последовательных неудач — `unhealthy`. `interval` задаёт период, `timeout` — время одной попытки, `retries` — порог неудач, `start_period` — время на инициализацию. В работе `pg_isready -U apiuser -d api` проверяет готовность сервера принимать подключения. Реальное выполнение SQL проверяет маршрут `/`. Сам статус `unhealthy` в обычном Compose не перезапускает контейнер автоматически.

### 27. Как переопределить или дополнить базовый compose.yaml (docker-compose.yml) файл для разных окружений (dev, prod)?

Общую конфигурацию кладут в `compose.yaml`. Для разработки можно добавить автоматически читаемый `compose.override.yaml` с bind mount исходников. Для отдельной производственной конфигурации указывают файлы явно, например `docker compose -f compose.yaml -f compose.prod.yaml up -d`. Правила слияния зависят от поля. Некоторые списки дополняются, скалярные значения могут быть заменены. Относительные пути разрешаются относительно первого файла. Итоговую модель проверяют командой `docker compose -f compose.yaml -f compose.prod.yaml config --quiet`. [Объединение файлов](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/)

### 28. Почему запускать процессы от имени root внутри контейнера — плохая практика? Как запустить контейнер от непривилегированного пользователя (non-root)?

Уязвимость процесса с UID 0 даёт атакующему больше возможностей изменить файлы и взаимодействовать с доступными устройствами или каталогами хоста. Контейнеру выделяют отдельную учётную запись и права только на нужные пути. В v6 созданы пользователь и группа `app`, затем задано `USER app`. Команда `id` показала `uid=999(app)`. Для уже готового образа возможен `docker run --user UID:GID ...`, если разрешения файлов позволяют запуск. [Фактический вывод v5 и v6](evidence/container-users.txt)

### 29. Как сделать файловую систему контейнера доступной только для чтения (read-only)? Как при этом работать с временными файлами?

`docker run --read-only --tmpfs /tmp IMAGE` делает корневую файловую систему доступной только для чтения и выделяет отдельный временный каталог в памяти. В Compose этому соответствуют `read_only: true` и `tmpfs: [/tmp]`. Путь для долговременных записей выделяют отдельно, например том PostgreSQL. При запуске проверяют все каталоги, в которые сервис пишет PID-файлы, кеш или данные.

### 30. Как безопасно передавать секреты (пароли, ключи API) в Docker и Docker Compose?

При сборке секрет передают через `docker build --secret` и читают в конкретном `RUN --mount=type=secret`. Во время запуска Compose можно определить `secrets` из защищённого файла, дать доступ нужному сервису и читать файл `/run/secrets/имя`. Образ PostgreSQL поддерживает `POSTGRES_PASSWORD_FILE`. В лабораторной конфигурации пароль задаётся через локальный `.env`, исключённый из Git. При такой схеме он виден пользователю с правом инспектировать контейнер. Для рабочего сервера применяют хранилище секретов, выдачу минимальных прав и ротацию. [Секреты Compose](https://docs.docker.com/compose/how-tos/use-secrets/)

### 31. Какие ограничения имеет Docker Compose при работе в Production? Почему для кластеров используют оркестраторы (Kubernetes, Docker Swarm)?

`docker compose up` развёртывает проект на выбранном Docker-хосте. Для одного сервера можно задать политику перезапуска. Если узел выйдет из строя, этот запуск сам не распределит экземпляры по другим узлам. Кластерный оркестратор планирует размещение, поддерживает нужное число реплик и управляет постепенным обновлением. Для отказоустойчивости базы отдельно решают задачи репликации и хранения данных. [Режим Swarm](https://docs.docker.com/engine/swarm/) · [Возможности Kubernetes](https://kubernetes.io/docs/concepts/overview/)

### 32. Что такое Docker Swarm? Чем он отличается от Kubernetes?

Swarm — встроенный режим Docker Engine для кластера. Управляющие узлы поддерживают согласованное состояние и размещают задачи сервисов на рабочих узлах. Например, сервису можно задать три реплики и политику поэтапного обновления. Kubernetes — отдельная платформа с API и контроллерами. Там контейнеры объединяются в Pod, Deployment управляет репликами и обновлением, Service даёт устойчивый сетевой адрес. Swarm удобен при опоре на Docker Engine, Kubernetes предоставляет больше расширений для сетей, хранения и контроллеров. [Docker Swarm](https://docs.docker.com/engine/swarm/) · [Kubernetes](https://kubernetes.io/docs/concepts/overview/)
