## Цель и вариант задания

Цель работы — изучить контейнеризацию на примере приложения, которое принимает HTTP-запросы и хранит данные в PostgreSQL. Для группы 13 методические указания БГУ на с. 11 предусматривают задания 1–4. Сначала проверялся отдельный контейнер Nginx, затем собственный образ с HTML. После этого приложение и БД запускались вручную и в составе проекта Compose.

Стенд первичного опыта — Windows, Docker Desktop 4.98.0 с WSL 2, Linux-контейнеры архитектуры amd64, Docker Engine 29.9.2. При контрольном запуске пакета использовался модуль Docker Compose v5.6.1. Ниже отдельно отмечены результаты исходного опыта и повторной проверки от 8 ноября 2026 г.

## Задание 3. FastAPI, PostgreSQL и оптимизация образов

Контейнер `simple-python-api` принимал запросы на `localhost:8001`. В пользовательской сети `lab1-net` приложение обращалось к `postgres-db:5432`, база `api`, пользователь `apiuser`. Исходный опыт использовал `postgres:16.2-alpine`. За HTTP-запросы отвечают FastAPI 0.110.2 и Uvicorn 0.29.0, а SQL-запросы выполняет psycopg2-binary 2.9.9. [Код приложения](../task3/simple_python_app/app.py) · [Версии зависимостей](../task3/simple_python_app/requirements.txt)

| Запрос | Что проверяет | Фактический ответ |
|---|---|---|
| `GET /` | Соединение с БД, `SELECT version()` | `message` = `Hello World`, версия начинается с `PostgreSQL 16.2` |
| `POST /items/test` | Запись строки, получение присвоенного БД идентификатора | `{"id":1,"name":"test"}` |
| `GET /items` | Чтение записей в порядке `id` | `[{"id":1,"name":"test"}]` |
| `GET /hello/Han` | Обработка параметра пути без обращения к БД | `{"message":"Hello Han"}` |

Первые три результата зафиксированы при выполнении задания. Маршрут приветствия и чтение существующей строки проверены при подготовке пакета. Идентификатор `1` относится к исходному набору данных. При повторной вставке PostgreSQL выдаст новый идентификатор. Для имени используется параметризованный запрос `INSERT INTO items (name) VALUES (%s) RETURNING id`. [Вывод контрольного чтения](evidence/running-lab.txt)

### Сравнение сохранённых образов

Размеры сняты **с исходных тегов** командой `docker image ls simple_python_app`. Первичный файл содержит v1 и v2. На этапе оформления считаны значения для всех семи сохранённых образов. Колонки воспроизводят два разных поля Docker Desktop. Диск учитывает локальное хранение образа, CONTENT SIZE отражает размер сжатого содержимого. Общие слои могут использоваться несколькими тегами. [Первичная запись](evidence/image-sizes-original.txt) · [Полный вывод Docker](evidence/image-sizes-review.txt)

| Тег | Dockerfile и особенность | DISK USAGE, MB | CONTENT SIZE, MB |
|---|---|---:|---:|
| `v1` | [Dockerfile](../task3/simple_python_app/Dockerfile) · Slim, зависимости до кода, `EXPOSE 8000` | 257 | 62.2 |
| `v2` | [Dockerfile.v2](../task3/simple_python_app/Dockerfile.v2) · тот же порядок слоёв, без `EXPOSE` | 257 | 62.2 |
| `v3` | [Dockerfile.v3](../task3/simple_python_app/Dockerfile.v3) · requirements через bind mount, кеш pip включён | 290 | 78.1 |
| `v4` | [Dockerfile.v4](../task3/simple_python_app/Dockerfile.v4) · тот же bind mount, `pip --no-cache-dir` | 257 | 62.2 |
| `v5` | [Dockerfile.v5](../task3/simple_python_app/Dockerfile.v5) · два этапа, Slim и wheels | 283 | 75.1 |
| `v5-alpine` | [Dockerfile.alpine](../task3/simple_python_app/Dockerfile.alpine) · два этапа, Alpine и libpq | 173 | 49.5 |
| `v6` | [Dockerfile.v6](../task3/simple_python_app/Dockerfile.v6) · вариант Slim с пользователем `app` | 283 | 75.1 |

- **v1 и v2.** Оба реальных Dockerfile уже устанавливают зависимости до копирования `app.py` и отключают кеш pip. Размеры совпали, а вторая сборка использовала кеш. Эта пара не позволяет определить влияние перестановки слоёв.
- **v3 и v4.** Отключение кеша pip при прочих одинаковых инструкциях уменьшило показанный DISK USAGE с 290 до 257 MB, разница 33 MB.
- **v5 и v5-alpine.** При сопоставимой двухэтапной схеме Alpine занял 173 MB против 283 MB у Slim. В итоговые образы скопирован каталог `/wheels`, и он остаётся после установки пакетов. В данной реализации v5 оказался больше v4.
- **v5 и v6.** Проверка `id` дала `uid=0(root) gid=0(root)` для v5 и `uid=999(app) gid=999(app)` для v6. Округлённые размеры двух образов совпали. [Вывод команды id](evidence/container-users.txt)

При подготовке пакета отдельно собраны все семь Dockerfile в Linux/amd64 и проверены импорты приложения, psycopg2 и Uvicorn. Таблица относится к ранее созданным образам. Сопоставимые длительности холодной и повторной сборки, потребление CPU/RAM и пропускная способность не измерялись.

## Задание 4. Nginx, API и БД в Compose

```text
Браузер → localhost:8085 → web (Nginx)
                              │ frontend-net
                              ▼
                        simple_python_app:8000
                              │ backend-net
                              ▼
                             db:5432 → dbdata
```

Nginx передаёт запрос на `http://simple_python_app:8000`. API использует имя `db` в сети `backend-net`. У БД есть именованный том `dbdata`. Команда `pg_isready -U apiuser -d api` проверяет готовность PostgreSQL. Условие `service_healthy` задерживает запуск API до успешной проверки. Внешний порт есть только у Nginx. [Манифест Compose](../task4/compose/compose.yaml) · [Конфигурация Nginx](../task4/compose/nginx/app.conf)

**Первичный опыт.** `docker compose config --quiet` завершилась успешно. При запуске база получила статус `Healthy`, API и Nginx — `Started`. Через порт 8085 браузер получил `Hello World` и версию PostgreSQL 16.2. После `docker compose down -v` были удалены том и сети, а `docker compose ps -a` показала только заголовки столбцов. [Снимок запуска и удаления ресурсов](evidence/compose-services.png) · [Ответ в браузере](evidence/compose-response.png) · [Список после остановки](evidence/compose-down.png)

**Повторный запуск из пакета.** Для проверки создан отдельный проект Compose с новым томом и паролем. Через Nginx прошли `GET /`, `GET /hello/Han`, `POST /items/test` и `GET /items`. После `docker compose down` и нового `up` строка с `id=1` сохранилась. В конце `down -v` удалил проверочный стенд. В журнале видны имена сервисов, состояние БД и ответы HTTP. [Протокол повторного запуска](evidence/compose-review.txt)

**Версия для публикации.** В исходном опыте задание 4 содержало копию сервиса из задания 3. В репозитории Compose использует общий код и `Dockerfile.v6` из задания 3. Пароль передаётся из локального окружения или `.env`. Порт 8085 привязан к loopback-интерфейсу. Эти изменения были включены в повторную проверку.

## Вывод

Отключение кеша pip дало измеримую разницу в паре v3/v4, а переход между двумя уже похожими Dockerfile v1/v2 сохранил размер. Вариант v6 позволил запустить API от пользователя `app` и через Nginx записать строку в PostgreSQL. Повторное создание контейнеров с тем же томом сохранило эту строку.
